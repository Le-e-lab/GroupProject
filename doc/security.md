# UPath Application Security Overview

This document outlines the security mechanisms implemented in the UPath Attendance Management System, including data protection measures, anti-fraud mechanisms, and recommendations for future security enhancements.

## 1. Authentication & Password Security

- **Hashing Algorithm:** User passwords are encrypted before being stored in the database using **bcrypt** with a work factor of 10.
- **Verification:** During login, `bcrypt.compare()` safely verifies the plaintext password against the stored hash. Plaintext passwords are never stored or logged.

## 2. Database Protection

- **SQL Injection Prevention:** The application heavily relies on the **Sequelize ORM** for database interactions. Sequelize automatically uses parameterized queries to sanitize input, protecting the application against SQL Injection (SQLi) attacks.
- **Input Validation:** Critical endpoints use basic validation on parameters to ensure expected data types and structures are received.

## 3. Anti-Fraud Mechanisms (Attendance)

- **Time-restricted Session Codes:** Attendance session codes generated by lecturers are strictly validated against a timestamp. The API uses the `otplib` library to generate and verify codes, creating a time-restricted window (default configured) during which the code is valid.
- **Geolocation Validation:** Physical class attendance requires the student's device to transmit GPS coordinates. The backend calculates the Haversine distance between the student and the lecturer/venue. If the distance exceeds the configured threshold (e.g., 50 meters), attendance is rejected.

## 4. Current Limitations & Areas for Improvement (CRITICAL)

While the database and passwords are secure, the current API implementation has a significant security vulnerability regarding **Authorization**.

### The Vulnerability: Client-Side Session Storage vs. Server-Side Tokens

Currently, successful login results in the backend returning a full user object to the frontend. The frontend Javascript stores this object in `sessionStorage` (`upath_user`) and relies on this stored data to dictate user role logic (e.g., hiding/showing admin panels, passing the \`studentId\` in requests).

**Why this is dangerous:**

1. **API Endpoints are exposed:** Most `/api/*` endpoints (fetching users, marking attendance, creating announcements) do not verify *who* is making the request. Any user with knowledge of the API structure could theoretically send a POST request with arbitrary data (e.g., modifying another student's attendance).
2. **Client-side spoofing:** A malicious user could edit their `sessionStorage` item in the browser developer tools to change their role from "student" to "admin". Since the backend doesn't challenge the frontend's claim of authority on many routes, this grants them unauthorized frontend access.

### Recommended Upgrade Path: JWT Implementation

To secure the application for production, the backend must adopt token-based authorization using **JSON Web Tokens (JWT)**.

1. **Login Generation:** Upon successful login (`/api/login`), the server should sign a JWT containing the user's ID and Role, secured with a strong `JWT_SECRET` stored in the `.env` file.
2. **Secure Delivery:** The JWT should be sent to the client as an `HttpOnly`, `Secure` cookie. This prevents XSS attacks from reading the token via JavaScript.
3. **Middleware Verification:** A global authentication middleware should be applied to all protected `/api/*` routes. This middleware will extract the JWT from the cookie, verify its signature, and attach the decoded user data (`req.user`) to the request object.
4. **Role-Based Access Control (RBAC):** Backend routes must verify the user's role before executing privileged actions (e.g., only `req.user.role === 'admin'` can delete users).
5. **Frontend Adjustments:** The frontend can still rely on `sessionStorage` for basic UI rendering logic, but all sensitive actions will fail at the backend level if the server-side JWT is invalid or lacks the required permissions.
